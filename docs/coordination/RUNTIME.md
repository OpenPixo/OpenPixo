# Native Codex integration

Updated 2026-10-25 (Asia/Tokyo). Owner: `runtime_core`.

## Delivered

- Native app-server create and resume use `workspace-write` and `on-request`. Windows/WSL no longer silently select full access; the existing explicit operator override remains.
- Both transports explicitly enable `multi_agent` for the owned process, matching the preserved M0's verified child-agent behavior without changing global Codex configuration.
- Each physical run owns its pending permissions. GET `/api/runs/:id/approvals` and POST `/api/runs/:id/approvals/:requestId` reuse run/project authorization. Only explicit `accept`, `decline`, or `cancel` is accepted; UUID request identities prevent another run's same RPC ID from resolving it. Closed/replayed responses return 409.
- Modern command/file requests, legacy command/patch requests, and Codex 0.160 permission profiles are supported. Profiles grant exactly the displayed permissions for the current turn. Native offered decisions are respected. Unknown server methods fail explicitly. Stale thread/turn requests are rejected.
- Pending requests appear in chat with command, directory, paths and additional permission details. User waiting pauses model-output/inactivity watchdogs. Cancellation clears pending requests and sends `turn/interrupt` with both native thread ID and turn ID; cancellation racing the turn-start response is covered. Approval "Cancel task" also invokes the existing run cancellation lifecycle with `user_stop`, so an interrupted native turn is recorded as canceled.
- Root session capture and completion are isolated from child thread notifications. Fragmented UTF-8 is decoded safely. Child lifecycle projection and npm native-binary layouts are recorded in [CODEX-EVENTS.md](CODEX-EVENTS.md).
- Enabled project skill bodies/source directories enter the existing prompt/resource pipeline. Project MCP config travels through the native `thread/start` / `thread/resume` RPC config; command arguments, environment values and HTTP headers stay out of process argv. Stdio and streamable HTTP are supported; legacy SSE fails clearly. A matching stored OAuth token is reused only for the same saved server ID and URL. The operator-only `exec-json` rollback rejects enabled project MCP with guidance to use app-server.
- CLI mirrors permission APIs: `pixo run approvals <runId> --json` and `pixo run approve <runId> <requestId> <accept|decline|cancel> --json`.

## Native provider correction

- Shared `nativeCodexProviderForConfig` accepts only OpenAI protocol with the canonical HTTPS DeepSeek root or OpenRouter `/api/v1` endpoint (optional trailing slash). Ports, credentials, queries, fragments and other gateways are excluded. Existing form snapshots and CLI BYOK flags are reused; omitted/legacy agent selection becomes native Codex and conflicting explicit engines fail clearly.
- Third-party runs use `openpixo_deepseek` / `openpixo_openrouter`, Responses transport, explicit create/resume `modelProvider`, no OpenAI authentication, and a dedicated process-only key. Provider, canonical endpoint, exact model and a credential fingerprint scope both the isolated native home and resume identity under the resolved daemon data root. User home/config/auth files remain untouched. Missing keys never fall back to the default account; ordinary account-backed Codex runs retain their existing behavior.
- DeepSeek's owned credential-free catalog declares Flash text/image and V4 Pro text, low/high/max reasoning, context and native tool metadata from the audited official contract. Its short neutral base template only satisfies the loader; the existing composed task/project/skill prompt remains authoritative. Forced detailed summaries are disabled. Known unsupported Pro image input and unsupported reasoning/model selections fail before spawn.
- OpenRouter uses the exact 0.160 command-auth schema and native model discovery, retaining returned model metadata. The fixed executable/argument vector reads a dedicated environment key and writes its raw token to the native auth pipe. Electron-as-Node mode survives into this helper, while the key is excluded from tool-shell inheritance. See [PROVIDER-FIDELITY.md](PROVIDER-FIDELITY.md) for actual offline native discovery evidence and its limits.
- `pixo run continue` accepts the same provider/model/env-key flags. A provider continuation without its snapshot fails before spawn. Keys are omitted from run persistence and scrubbed from CLI responses, displayed event text and raw diagnostic streams; correlation IDs and decision enums remain unchanged.
- Settings connection tests use the same canonical `/responses` endpoint and wire shape. This tests service connectivity only; it does not certify code/tools/images or native task completion.
